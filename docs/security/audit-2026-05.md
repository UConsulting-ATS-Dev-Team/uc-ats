# UConsulting ATS — Platform Security Audit

**Date:** 2026-05-28
**Scope:** `server/`, `client/` (excluding third-party dependencies and infrastructure)
**Resolves:** Issue #30 (flagged by Ayan)
**Reviewer:** automated platform audit

## Executive Summary

12 concrete security findings identified across authentication, authorization, file access, secrets management, transport hardening, and email handling. **7 are HIGH severity** (directly exploitable by any authenticated candidate or by anyone on the open internet), **5 are MEDIUM severity** (require chained conditions but have significant impact). All HIGH findings and the most impactful MEDIUM findings are remediated in the accompanying PR; a small number of MEDIUM items are tracked as separate follow-ups.

Severity legend:
- **HIGH** — directly exploitable, leads to authentication bypass, privilege escalation, or PII/data breach.
- **MEDIUM** — exploitable under specific conditions or only by an authenticated attacker, still meaningful impact.
- **HARDENING** — defense-in-depth, no direct exploit identified.

---

## HIGH severity

### H1. Hardcoded fallback JWT secret

**Location:** `server/src/config.js:21`

```js
jwtSecret: process.env.JWT_SECRET || 'fallback-secret-key',
```

**Impact:** If `JWT_SECRET` is unset in any environment (e.g., a misconfigured deploy, a developer running against the prod DB locally), the server silently falls back to a public, source-controlled string. Anyone reading the public repo can forge JWTs for any user — including `ADMIN` — and bypass authentication entirely.

**Exploit:**
```js
jwt.sign({ userId: '<known admin id>', email: 'admin@…', role: 'ADMIN' }, 'fallback-secret-key')
```

**Fix:** Throw at startup if `JWT_SECRET` is missing.

---

### H2. Hardcoded member-registration access token

**Location:** `server/src/routes/auth.js:275`

```js
const requiredToken = 'member-access-2024';
if (!accessToken || accessToken !== requiredToken) { ... }
```

**Impact:** Anyone who reads the repo (public or accidentally leaked source) or guesses the predictable string can self-register a `MEMBER` account via `POST /api/auth/register-member`. `MEMBER` accounts can view candidate PII, grade applications, and access interview materials.

**Fix:** Read from `MEMBER_REGISTRATION_TOKEN` env var; rotate immediately upon merge. (Follow-up: replace self-serve registration with an admin-invite flow.)

---

### H3. JWTs never expire

**Location:** `server/src/routes/auth.js:83-86, 128-131, 324-327`

```js
jwt.sign({ userId, email, role }, config.jwtSecret); // no expiresIn
```

**Impact:** Tokens are valid forever, until the user row is deleted or the secret rotated. Combined with `localStorage` storage on the client (M2), any single XSS, lost laptop, or browser-extension compromise gives permanent access. There is no logout-equivalent on the server side.

**Fix:** Add `expiresIn: '8h'` to all three `jwt.sign` calls. Existing tokens continue working until users naturally re-login.

---

### H4. IDOR — any authenticated user can read any application

**Location:** `server/src/routes/applications.js:771-854` (`GET /api/applications/:id`)

```js
const application = await prisma.application.findUnique({ where: { id } });
res.json(application);
```

**Impact:** Endpoint is gated by `requireAuth` only — no ownership check. Any candidate (`USER` role) can enumerate IDs (sequential cuid-equivalent or by scraping references) and read every other applicant's full record: resume URL, cover letter URL, GPA, contact info, review scores. This is a PII breach class issue.

**Fix:** Gate the handler: `ADMIN`/`MEMBER` see all; `USER` may only see applications they own (`application.candidate.userId === req.user.id` or `application.candidate.email === req.user.email`).

---

### H5. IDOR — any authenticated user can grade any application

**Location:** `server/src/routes/applications.js:618-681` (POST grade handler)

**Impact:** Same root cause as H4 — `requireAuth` without role/team check. A candidate can inject favorable scores for themselves or sabotage other applicants. Compromises the integrity of the entire selection process.

**Fix:** Restrict grading endpoints to `ADMIN`/`MEMBER` role (via `requireAdminOrMember`). Optionally further restrict `MEMBER` to applications their review-team is assigned to.

---

### H6. IDOR — Google Drive file proxy serves any file ID

**Location:** `server/src/routes/files.js:11-83`

```js
router.get('/:fileId/image', async (req, res) => {
  const { fileId } = req.params;
  const fileStream = await getFileStream(fileId);
  fileStream.pipe(res);
});
```

**Impact:** Authenticated user supplies any Google Drive file ID — including IDs the service account can access but the user has no business reading — and the server streams it back. Resume PDFs, headshots, cover letters all become accessible to any logged-in candidate who learns a file ID. File IDs leak into other application records and into the React app's network traffic.

**Fix:** Before streaming, verify the `fileId` is referenced by an `Application` the caller has rights to view (same authorization rule as H4).

---

### H7. `POST /api/applications/manual` is reachable by any authenticated role

**Location:** `server/src/routes/applications.js:129-250`

**Impact:** The endpoint is gated by `requireAuth` (line 126) but no role check, so any authenticated user — including a candidate (`USER`) — can create arbitrary `Application` and `Candidate` rows in the active recruiting cycle from request-body data. Candidates can forge applications under other peoples' student IDs / emails, contaminating the pipeline and downstream sync logic.

**Fix:** Add `requireAdmin` to the handler. If the endpoint is unused by the admin UI, delete it.

## MEDIUM severity

### M1. Password-reset token logged in plaintext

**Location:** `server/src/routes/auth.js:204-218`

```js
const resetLink = `${config.clientUrl}/reset-password?token=${resetToken}`;
console.log('Sending email to:', email);
console.log('Using user:', process.env.EMAIL_USER);
console.log('Reset link:', resetLink);
```

**Impact:** Anyone with read access to server logs (Railway dashboard, log aggregator, anyone shoulder-surfing during a debug session) can lift the token and take over the account before the legitimate user clicks the email. Also leaks the operational Gmail address.

**Fix:** Remove the three `console.log` calls. If debugging email send failures, log only success/failure booleans and the SMTP-side message ID.

---

### M2. JWT stored in `localStorage`

**Location:** `client/src/context/AuthContext.jsx:9, 48, 62, 76`

**Impact:** `localStorage` is readable by any JavaScript in the same origin. Any reflected/stored XSS exfiltrates the (non-expiring, per H3) admin token. The combination of H3 + M2 turns a single XSS into permanent persistent compromise.

**Fix (short-term):** addressed partly by H3 (token expiry).
**Fix (long-term, separate issue):** move JWT into an `httpOnly; secure; sameSite=strict` cookie and add CSRF protection. This is an architectural change and is scoped as a follow-up issue.

---

### M3. CORS open to all origins

**Location:** `server/src/index.js:21`

```js
app.use(cors());
```

**Impact:** Default `cors()` echoes any `Origin` and permits credentialed requests when paired with a same-site cookie. The current threat is muted because tokens are in `localStorage` (which CORS does not auto-attach), but any future move to cookies would immediately become CSRF/SOP-bypass vulnerable. The endpoint also leaks responses to any origin a victim's browser visits.

**Fix:** Lock to the production client origin via `CORS_ORIGIN` env var; allow `localhost:5173` in development.

---

### M4. No security headers (no `helmet`)

**Location:** `server/src/index.js` (absent)

**Impact:** Missing CSP, `X-Content-Type-Options`, `Referrer-Policy`, HSTS, `X-Frame-Options`. Expands blast radius of any future XSS, increases data leaked via referer, allows clickjacking of the admin UI.

**Fix:** `app.use(helmet())` with sensible defaults; tune CSP later if needed.

---

### M5. Email HTML injection in notification templates

**Location:** `server/src/services/emailNotifications.js` — multiple sites (lines 29, 38–39, 73, 182, 326, 773–776, 843–860 among others)

```js
html: `<p>Dear ${candidateName},</p>
       <p>You RSVP'd to ${eventName} at ${eventLocation}.</p>`
```

**Impact:** Candidate-controlled fields (`candidateName`, `candidateEmail`, `eventLocation`, `studentId`, `memberName` when the member is candidate-supplied) are interpolated raw into HTML email bodies. A candidate registering with name `<a href="https://evil/">Click here</a>` weaponizes every downstream notification to staff (phishing-by-proxy through a trusted sender), and the email client renders attacker HTML inside the org's branded template.

**Fix:** Introduce a small `escapeHtml` helper and wrap every candidate-controlled interpolation site. (Done in remediation PR.)

## HARDENING (defense-in-depth)

### D1. `express.json()` has no payload limit

**Location:** `server/src/index.js:22`

**Recommendation:** `app.use(express.json({ limit: '1mb' }))`.

### D2. No global error handler — handlers individually decide what to leak

**Location:** scattered

**Recommendation:** Add a final `app.use((err, req, res, next) => ...)` that returns a generic `500 { error: "Internal server error" }` and never echoes `error.message`. Several handlers currently return `error.message` to clients (see `server/src/routes/applications.js:244, 765, 849, 1035, 1178, 1204, 1348` and `server/src/index.js:86`).

### D3. Member-registration model

The hardcoded token (H2) is a workaround for the absence of an invite flow. Recommend replacing self-serve `POST /register-member` with an admin-issued single-use invite link. Tracked as a follow-up issue.

### D4. No automated test suite

There is no `npm test` target. Security regressions cannot be caught automatically. Recommend adding at minimum a smoke suite that hits `/api/auth/*`, the ownership boundaries of `/api/applications/:id`, and the file proxy.

## Post-Merge Action Items

1. **Rotate `MEMBER_REGISTRATION_TOKEN`** — generate a fresh value and set it in every deployed environment. The string `member-access-2024` must be considered compromised.
2. **Rotate `JWT_SECRET`** if there is any chance the previous deploy ever ran without the env var set (which would have used the public `fallback-secret-key`).
3. **Rotate the operational Gmail app password** (`EMAIL_PASS`) — the address was logged historically and should be considered exposed.
4. **Audit existing `MEMBER` accounts** for ones the team did not personally invite.
5. **Inform any candidate whose application detail was viewed by another candidate** if logs allow detection.
